# AGENTS.md

Project knowledge for working on the MailCraft editor. Host-facing API docs live in [README.md](README.md).

## Workflow — always

- After any change under `src/` **or to README.md/DOCS.md**: `node build.js`. The demo page (`examples/vanilla.html`) loads `dist/mailcraft-editor.bundle.js`, never `src/` — a change isn't visible until the bundle is rebuilt. The same run regenerates the "Every message key" appendix in DOCS.md (from `src/core/i18n/en.js`, between the `message-keys` markers — never edit the table by hand) and the byte-exact `DOCS.md.txt`/`README.md.txt` mirrors the docs site serves raw (the "Copy for AI" button and `llms.txt`); `test/system.test.mjs` fails when any of them drift. Double-clicking the demo works: the example emails are inlined in it as `<script type="text/x-template">` blocks, so nothing is fetched. The same emails also live as standalone files in `examples/templates/` (byte-identical copies, for hosts to lift); those are not what the demo reads.
- `npm test` runs 13 suites (see the `test` script in package.json). `storage`, `export`, `templates`, `system` and `toolbar` are DOM-free and dependency-free; the rest (`editor-dom`, `css-cascade`, `render-dom`, `import-html`, `interaction`, `focus-preserve`, `shortcuts`, `import-structure`) drive the element and the importer on **jsdom** (a devDependency, alongside esbuild and c8). `npm run coverage` wraps the same suites in c8.
- The importer is covered by `test/import-html.test.mjs`, `test/import-structure.test.mjs` and `test/css-cascade.test.mjs` (jsdom). jsdom is not a real layout engine, so anything that depends on computed layout is still verified by hand through the Code modal — or by driving a scratch page through headless Chrome (`chrome.exe --headless=new --dump-dom`).
- Documents persist in `localStorage` **per browser tab** (`mailcraft.v3.tab.<id>`, seeded from the shared `mailcraft.v3`). An already-imported document keeps its old values — rebuilding does not retroactively fix it; re-import through the Code modal to see importer changes.
- Multiple sessions/tools may edit this repo concurrently — expect files to change on disk mid-session and re-read before editing. Source files carry **mixed CRLF/LF line endings**, so exact-match edits can fail on the newline alone.

## Build system constraints

`build.js` is a deliberate zero-dependency bundler with a regex transform. It only understands:

- `import { a, b as c } from '...'` (single-line)
- `export { a, b } from '...'`, `export const|function|class|async function NAME`

No `export default`, no bare `export { ... }`, no multi-line imports, no dynamic `import()`. A new file using anything else fails the build with "unhandled export syntax".

The generated bundle is then minified through esbuild (a devDependency) with an external sourcemap. `require()` is unavailable in `build.js` (the package is `type: module`) — it goes through `createRequire`. If esbuild is missing the build falls back to the readable bundle and deletes any stale `.map`, so a clone with no `node_modules` still produces a working `dist/`; that fallback is worth exercising after touching the build (`mv node_modules/esbuild node_modules/_off && node build.js`). Minifying buys ~30% raw and ~30% gzipped (245 KB → 172 KB) — the payload is mostly string data (the 31 i18n tables are ~371 KB of source on their own), which gzip compresses and a minifier cannot.

## Architecture

- `src/core/` — state and logic, **no DOM rendering** (EditorCore in `editor-core.js`: setState + rAF-batched emit; full re-render, no diffing). `src/render/` — all DOM building. The canvas is torn down and rebuilt per state change; focus/caret survive via `data-focus-key` + `render/focus-preserve.js`. Any new focusable field needs a stable focus key.
- Shadow DOM everywhere: `window.getSelection()` lies (use `core.getSelection()`), and window-level event listeners see retargeted `e.target` (the host element) — use `e.composedPath()[0]`.
- Inspector fields are descriptors (`core/binder.js`) rendered by `render/fields.js`. Toggle state flows through `on` → `aria-checked`. Number-like inputs are `type="text"` + `inputmode` on purpose (number inputs break caret restoration).
- Rows → columns → blocks. Row padding: linked `py`/`px` pair with optional per-side overrides `pt/pr/pb/pl` + `padSplit`; border sides `bTop/bRight/bBottom/bLeft`; `shadow` is a raw CSS string. Columns optionally carry `bg`/`radius`/`padY`/`padX`. `mkRow` defaults + `migrateDoc` backfill keep old saved docs valid — never make a renderer require a prop without a fallback.
- Export (`core/export.js`) reads back the rendered DOM (`grab`); renderer changes affect exported HTML directly. Import and export are meant to stay round-trip-compatible; `test/import-html.test.mjs` pins one round trip ("exported output re-imports"), but check anything beyond that shape by hand.
- Dynamic content is start/end marker *blocks* (`condition`/`loop`, props `{ expr, end }`; `insertBlock` drops the pair, at row level as a slim row each). The editor never evaluates them: export computes `logicPlan` document-wide (stray ends emit nothing, unclosed opens auto-close after the last row) and emits literal `{{#if}}`/`{{#each}}` at each marker's position — marker-only rows emit no `<tr>`. Import restores them: `foldLogicWrappers` turns between-row tags into synthetic `data-mc-logic` rows before DOMParser can foster-parent the text, `logicMarkersOf` classifies bare in-cell tags; tags mixed into prose stay text. The Code modal's preview iframe shows them via `decorateLogicTags` (display-only — the source, export, copy and download all keep the literal tags).
- i18n: chrome strings in `core/i18n/en.js` (other locales overlay, English is the fallback); inspector field labels are deliberately hardcoded English (separate pass, see en.js header). The `locale` attribute resolves shipped tables via `core/i18n/tables.js`. Adding a key to `en.js` means adding it to all 30 locale files in the same commit — `test/system.test.mjs` compares key sets, because the English fallback otherwise hides an untranslated key behind plausible-looking UI.
- Lifecycle ordering is load-bearing. `EditorCore` is built in the element's **constructor** (so a host can configure before insertion), but `mount()` runs from `connectedCallback` and restores the persisted draft. `EditorCore.docSetByHost` (set by `loadTemplate`/`importHtml`/`loadDoc`) and `EditorCore.mounted` gate that restore: without them, `createElement()` → `loadTemplate()` → `append()` silently replaced the host's template with the previous draft, and re-connecting the element (a framework remount, or a move in the DOM) did the same to a live document. Any new "host pushes a document in" entry point must set `docSetByHost`, and must run its input through `normalizeDoc` (`core/blocks.js`) — sparse or foreign JSON used to reach the renderer intact and fail later at export on `theme.font`. `normalizeDoc` seeds the theme, row props, column spans, per-type block props and ids, keeps legacy block types for `migrateDoc` to convert, and returns `null` when there is nothing usable so a caller no-ops instead of clearing the document. It is a no-op for anything the importer produced — verified by diffing an HTML import before and after. At module scope, `MailCraftEditor` extends a `typeof HTMLElement !== 'undefined'` stand-in and `customElements.define` is wrapped in a `customElements.get` check — the package must stay importable under SSR and in Node test runners, and must survive being evaluated twice (HMR, or a bundled and an ESM copy side by side).
- The host-facing contract is **HTML in, HTML out** — `loadTemplate({ html })` / `exportHtml()`, with round-tripping as the way a draft is saved and restored. The document object is an internal representation: `getContent`/`setContent` still exist (undo, autosave and the tests need them) but are marked internal and appear nowhere in README.md, so its shape is free to change. Anything new that would make a host learn that shape belongs behind the HTML seam instead.
- There is no `campaign`/title setting — attribute, property, state key and the per-document export `<title>` were all removed on 2026-08-30. The exported title is the fixed string `Email` and downloads are `email.html` / `email.png`. `persist()` lost its second parameter in the same pass (`persist(doc, assets, chrome)`).
- `src/create-editor.js` is the mount-into-a-container API (`createEditor(target, options)`), a thin wrapper over the element: it creates the tag, splits options into attributes (strings) and properties (objects/functions), and returns a forwarding handle. It is covered by the `createEditor` section of `test/editor-dom.test.mjs` (jsdom); behavior jsdom cannot see (real layout, real height) is still verified by hand in a browser. Two ordering rules it depends on: `toolbar` and the providers are set *before* insertion (the header is built once, at mount), and `html` is applied *after* (it is an undoable edit).
- The top bar is host-configurable through `core/toolbar.js` (`toolbar` attribute/property; see README). Two things to know before touching the header: every refresher (`renderInner`, `refreshSavedLabel`, `renderDeviceSeg`, `refreshStrings`) has to tolerate a node that was never built, and `render/style.js` pins `grid-template-rows` with `!important` — a shell built without a header carries `.mc-no-header` so that rule can step aside, otherwise the canvas renders into a 62px sliver.
- Templates are host content **and host UI** — the editor has no Templates tab, no gallery, and ships no catalogue (the in-editor gallery and `editor.templates` were removed on 2026-08-30; `core/templates.js` had been deleted the same day). The whole seam is `editor.loadTemplate(tpl)` with one of three sources: `doc` (document object), `build()` (made per use), or `html` (raw email, run through the importer via the shared `parseHtmlSource` fallback — content is never dropped). A fresh editor opens on `blankDoc()` (one empty row). Example templates are plain HTML files in `examples/templates/`, mirrored inline in `examples/vanilla.html`'s host-side picker. Covered by `test/templates.test.mjs` (in `npm test`).

## Conventions

- Comments explain *why* (the bug a guard prevents, the constraint that forced a shape) — match the existing density; no change-narration comments.
- Inspector labels use plain, non-technical language ("Rounded corners", "Space inside — top & bottom"); developer-grade controls go behind the "Advanced options" switch.
- Primary/accent color is `#0065b3` (dark-chrome variant `#58a8e3`), set via `--ed-*` tokens in `render/style.js`.
- Upload policy is the host's: no default `storageLimits`, byte-sniffed formats, SVG needs the explicit `allowSvg` second opt-in.
- The runtime stays plain JavaScript; TypeScript support is the hand-written `types/index.d.ts` (wired via `types` + the `exports` `"types"` condition in package.json). It describes only the public contract, and internals (`EditorCore`, the document object) stay loosely typed on purpose. Changing the public surface — an export in `src/index.js`, an element attribute/property/method/event, a provider or limits shape — means updating that file in the same commit. Nothing checks the sync automatically.
